# Architecture

[Project overview](../README.md)

This document describes the implemented application. Requirements, delivery order, and planned extensions remain authoritative in [the implementation plan](../IMPLEMENTATION_PLAN.md).

## Workspace boundaries

- `apps/web`: React SPA using React Router Data Mode. It renders validated API data and owns forms, navigation, and page feedback.
- `apps/api`: Fastify application owning authentication, authorization, financial validation, persistence, and all FMP communication.
- `packages/contracts`: browser-safe Zod schemas, the generated OpenAPI document, and types shared across the API/browser boundary.
- PostgreSQL and Prisma store users, sessions, wallets, shared instruments, and immutable BUY/SELL transactions. Future read models and pricing persistence follow their mapped delivery slices.

The browser calls the application API, and the API calls FMP. Financial amounts cross the boundary as exact decimal strings with explicit currency. The current application supports USD only.

## FMP provider boundary

The API-only adapter lives in `apps/api/src/providers/fmp/` and uses FMP's [stable API](https://site.financialmodelingprep.com/developer/docs/quickstart). `FMP_BASE_URL` defaults to `https://financialmodelingprep.com/stable/`; overrides must use HTTPS, with loopback HTTP allowed for local fake providers outside production. Do not include credentials, query parameters, or fragments in the base URL. `FMP_API_KEY` may remain empty while provider features are unused; an attempt without a key returns `NOT_CONFIGURED` without reserving quota or making an HTTP call. Live credentials belong only in ignored `.env.local` or the API's hosted secret manager, never a `VITE_` variable or browser-importable package.

Each adapter `request` performs one GET attempt and requires an injected `reserveRequest` function. That function must atomically reserve one shared budget unit immediately before dispatch, returning false on exhaustion. Reservation errors fail closed. Dispatched HTTP errors, transport failures, timeouts, invalid JSON, invalid response shapes, and provider error envelopes retain their charge. The timeout defaults to 10 seconds and includes response-body consumption. Results contain safe failure codes and HTTP status only; raw provider bodies, URLs, keys, and transport exceptions are not returned or logged.

The transport makes no automatic retries, redirects, profile follow-ups, or pagination calls. A caller explicitly retries or requests a follow-up through the same adapter, reserving another unit each time. Cached results bypass the adapter entirely. The adapter validates responses against internal Zod schemas. Historical responses use a dedicated JSON parser that preserves the original numeric closing-price token before decimal validation.

Normal startup uses durable PostgreSQL quota reservations, with a persisted policy and one counter per quota day. Shared dated price snapshots, wallet subscriptions and fenced refresh leases support a process-local, symbol-deduplicated `p-limit` scheduler; see [market-data scheduling](market-data.md). The FMP plugin registers the scheduler, quote adapter and startup reconstruction of unfinished intent. Its close hooks cancel waits, reject new work and drain active persistence before Prisma disconnects. Process signals call Fastify close once. The market-data service exposes cached valuation, durable refresh/status and shared quota endpoints. Browser wallet-open triggers follow in 7E. There is no production in-memory quota fallback. Controlled callers can pass `buildServer({ fmp: { budget: { read, reserveRequest }, fetch?, timeoutMs? } })` to exercise providers with one explicit test budget shared by transport reservations, refresh admission, quota status and recovery and `recoverRefreshWork: false` to disable startup reconstruction in tests/tooling. Normal deployed dispatch uses the durable store. Automated tests use controlled providers and assert quota deltas without live calls. For availability and configuration, see [provider availability](api.md#provider-availability).

## Ledger persistence and wallet ownership

The transaction service prepares an internal command: BUY requires verified instrument metadata, while SELL excludes that metadata. Shared instrument and command types live in the domain layer. The repository prepares the instrument under the wallet lock, checking symbol/currency consistency before any BUY upsert.

The server checks wallet ownership before contacting FMP and verifies it again under a database lock before inserting. Missing and foreign wallets both return `404` without provider dispatch. Concurrent BUYs and SELLs share a wallet row lock, which also coordinates with wallet deletion. BUY provider calls happen before the database transaction, so a wallet deleted during verification returns `404` without ledger or instrument writes; an already dispatched profile request still consumes its reserved quota unit. SELL uses persisted instrument metadata without contacting FMP.

The write transaction explicitly uses `ReadCommitted` isolation. It acquires the owned wallet with `SELECT ... FOR UPDATE`, inserts the candidate, reads the affected symbol's complete ledger, and runs FIFO replay using persisted IDs and timestamps. Ledger reads after the lock see the preceding writer's commit. If any historical sale oversells, a private rollback exception rejects the Prisma transaction; the repository catches it after rollback and returns `INSUFFICIENT_HOLDING` as a normal `Result` failure. Returning a failure object from inside Prisma's transaction callback would commit the inserted row, so that rollback exception stays confined to this boundary. This follows PostgreSQL's [locking and consistency guidance](https://www.postgresql.org/docs/17/applevel-consistency.html). Locks serialize all symbols within a wallet; separate wallets can write independently.

The database stores shared instrument records and wallet-owned transactions. Deleting a wallet cascades its transactions and refresh subscriptions; shared instruments survive even when their last wallet is deleted, and other wallets retain their transactions. Referenced instruments cannot be deleted. PostgreSQL integration tests cover these guarantees, numeric boundaries, exact concurrent totals, ownership, immutable rows, rollback, and deletion during profile verification. Slice 7A additionally verifies shared price/quota/work preservation and cascading refresh-subscription cleanup.

Refresh subscriptions reference wallets with cascading cleanup. Global price snapshots, quota accounting and symbol work remain independent of wallet ownership; deleting one subscription preserves work needed by another wallet. Retained work without subscriptions cannot acquire another lease and is excluded from recovery. Real PostgreSQL regression tests verify persistence, scheduling, restart reconstruction and shutdown ordering. Pending retries preserve their attempt count/deadline; terminal failures await a later explicit request and never become recurring refreshes.

The pure [accounting core](accounting.md) replays one wallet/instrument ledger in deterministic order, consumes original acquisition lots using FIFO, and calculates remaining cost basis, weighted-average unit cost, and realized P/L with exact decimal arithmetic. It is independent of persistence and HTTP. Ledger read endpoints reuse this core on a consistent owned-wallet snapshot, without taking the wallet write lock or calling the provider.

The ledger read repository selects the owned wallet and its matching transactions/instrument metadata inside a short `RepeatableRead` transaction, then releases the snapshot before service-side FIFO replay and response mapping. Read routes use a dedicated ledger service, independent of instrument verification. Shared row-to-ledger and row-to-transaction mappers keep read and write date/decimal serialization aligned. The existing wallet lifecycle DTOs retain their metadata-only shape; the holdings endpoint carries financial summaries. Pagination limits history output, but replay still loads the complete matching ledger; materialization or incremental accounting is deferred until actual ledger size warrants it.

Transaction creation and latest-only deletion use the repository's shared `withLockedWallet` transaction boundary, including the ownership check, `ReadCommitted` isolation, wallet row lock, and rollback mapping. Deletion scopes the target to that wallet, checks it against all entries for its instrument with the same comparator as FIFO, and hard-deletes only when it is latest. The remaining immutable entries are replayed from the locked snapshot before commit. Conflicts preserve all rows; no deleted-row audit copy is kept. See [the deletion API](api.md#latest-transaction-deletion).

Endpoint behavior and provider request costs are documented in [API behavior](api.md). Price persistence and refresh coordination remain in the [delivery slice map](../IMPLEMENTATION_PLAN.md#delivery-slice-map).

## Route configuration

The web app uses React Router Data Mode. [`router.tsx`](../apps/web/src/app/router.tsx) owns the typed `RouteObject` tree, and [`main.tsx`](../apps/web/src/main.tsx) mounts its `RouterProvider`. Route components are ordinary modules imported directly by route objects; folders are not file-system routes. Use nested routes with layout components and `<Outlet />` when routes share a shell. Keep each route's component and any future loader, action, or error boundary with the route behavior it owns. Keep the router focused on route composition, use direct imports instead of convenience re-export files, and load or mutate server state through route data APIs that call the typed API client.

Page-essential reads use `requirePageData` to return validated data or throw a safe route failure. A shared boundary below the authenticated layout keeps navigation available. Expired sessions redirect to login; wallet detail and purchase loaders treat invalid IDs, missing wallets, and inaccessible wallets as the same unavailable page. Other forbidden reads show access denied. Transient failures offer a GET revalidation retry, delayed by `Retry-After` when supplied; retry never replays a mutation. Unexpected exceptions show generic feedback with a page reload. Form submissions and inline stock/quote lookups retain their local error handling so recoverable failures preserve entered values.

Wallet and purchase loaders/actions bind cancellation once with `createRequestClient(request.signal)`, then compose the domain APIs they need, such as `createWalletApi(client)` or `createPurchasesApi(client)`. Each invocation gets its own typed HTTP client and result handler; multiple domain APIs can share that client, and endpoint methods receive only their business inputs. New domain APIs use the shared client without registration in a central catalogue. The shared client propagates cancellation to HTTP and throws cancellation reasons before dispatch or after a late response, keeping cancelled work out of normal error and success feedback. Action-body parsing retains its own cancellation checks. Cancelling a dispatched mutation does not guarantee server rollback, so uncertain purchase outcomes still require their existing handling. Better Auth uses a separate client and is outside this cancellation binding.

Price-refresh scheduling uses `defaultShouldRevalidate: false` for both automatic and manual fetcher submissions. When a new refresh result settles, `useWalletPricing` explicitly reloads valuation/status and the shared quota resource once, including after a rejected request. A result-reference guard prevents repeated reads when the fetcher or quota context updates again. This keeps wallet metadata, ledger loaders and the parent session loader out of price-only updates; financial mutations and explicit ledger recovery retain normal router revalidation, and pricing requests still redirect expired sessions to login.

Timed price checks use a separate status-only fetcher. Unchanged pending/running work does not reload valuation or quota; changes to per-position freshness, terminal work transitions, or a valuation behind completed status trigger a full pricing read. The full pricing fetcher keeps its original resource URL so financial mutations still revalidate valuation even after background polling. Polling retains its bound, cancellation, and last-known values. Quota refreshes on its shared interval and explicit pricing checks rather than on each progress tick.

The refresh-status API reads an ownership-scoped PostgreSQL summary of BUY-minus-SELL quantities, including zero-quantity closed positions, in one statement. It then reads shared prices/work only for open symbols. Status reads do not load transaction DTOs or execute FIFO replay; financial valuation still uses the accounting core. See [the polling measurement](price-polling-performance.md) for regression coverage and a 10,000-row comparison. The public API schemas and database schema are unchanged.

Wallet and instrument pages delegate pricing subscriptions to dedicated pricing components. Wallet metadata, ledger summaries and transaction history sit outside those update boundaries. The valuation adapter retains the last successful value for its wallet and reuses the previous snapshot when a validated response is value-identical; shallow memo boundaries keep unchanged holdings and price metrics from repeating financial formatting. The quota controller lives in its provider, with separate contexts for data/refresh commands and loading state. See [pricing render verification](pricing-render-isolation.md) for evidence and the remaining closed-dialog work.

## Wallet deletion journey

The wallet detail page offers a permanent-delete flow with an irreversible warning followed by a final warning and exact-name confirmation. Matching is case-sensitive and preserves spaces. The final delete button must be explicitly activated; Enter in the name input does not delete. Cancel or Escape before submission keeps the wallet and resets the confirmation. While submitting, the controls are disabled and the dialog stays open. Successful deletion returns to a refreshed wallet list. Failures display safe feedback without claiming success; an uncertain network result asks the user to check the wallet list before retrying. The browser route action checks the latest wallet name before sending DELETE; API ownership checks remain authoritative.

## Purchase journey

The wallet detail page links to `/wallets/:walletId/buy`. Search by symbol or company name, select a verified USD result, choose the trade date, and enter quantity and an optional description. The page displays the closing price, its effective date, and the exact decimal price that will be saved. Changing the search, stock, or date invalidates the previous price. Weekend/holiday fallback preserves the selected trade date. The API remains authoritative for stock eligibility, ownership, currency, and validation. A successful save returns to the wallet with a toast; an uncertain save blocks resubmission on the page to reduce duplicate purchases. The wallet now shows the saved purchase in its ledger history. Normal provider requests use the durable shared quota when the key and migration are configured; the automated purchase journey uses an injected fake and needs no real FMP key.

## Ledger, sale and transaction deletion journeys

Wallet detail loads the lifecycle metadata, ledger summary, and paginated history. `/wallets/:walletId/instruments/:symbol` shows one instrument's remaining acquisition cost, weighted-average remaining unit cost, realized FIFO P/L, last trade date and symbol-filtered history. Closed positions retain realized results and disable selling. Labeled Card records show every trade field on narrow screens and expand their field grid on larger screens; a desktop table is unnecessary for this presentation. Dates stay native inputs pending the separate date-picker work.

The sell Dialog uses React Hook Form and a schema derived from the transaction contract. It displays exact available shares, accepts an execution price, validates input precision/date/current quantity, and previews proceeds with string/BigInt arithmetic. Client checks do not replace the server's historical-balance validation. Browser formatting uses decimal strings and half-up rounding for amounts (2 places), unit prices/average cost (4), and shares (up to 6); FIFO accounting remains entirely on the API.

Sale triggers share one mutation controller per holdings view. Only the selected position creates a form, resolver and default trade date; ordinary cancellation or success unmounts that editor. An uncertain result retains its editor while closed and blocks selecting another position until explicit ledger recovery. Its original trigger can reopen the recovery UI even if a later read reports zero shares, while submission remains blocked. Per-row Radix Dialog roots preserve trigger focus without per-row form or fetcher setup. See [sale editor lifecycle](sale-editor-lifecycle.md) for verification and scope.

A resource route action at `/wallets/:walletId/transactions` binds its request signal to the shared client and composes the transactions API locally. The modal uses a fetcher so submission preserves the current route and values on rejection. Latest-only delete buttons come from the server's `canDelete` flags; an AlertDialog confirms irreversible removal and its effect on holdings and P/L. Stale eligibility remains a server conflict. Successful actions revalidate active summaries/history; removing the final instrument entry returns to wallet detail, and history pages beyond the new last page redirect to an available page.

Pending dialogs disable repeated submission and closing. Sell and transaction-delete dialogs share fetcher outcome handling, while sale validation stays with the form. Sale dialog state is scoped to the wallet/instrument identity, so navigating to another position starts a fresh form; refreshing the same position preserves entered values. Rejections remain inline with a manual ledger refresh; network failures, server errors and invalid success receipts warn that the outcome is unknown and block resubmission until the user refreshes/checks the ledger. No financial mutation is retried automatically. Mobile dialogs fill the viewport and scroll internally. Empty/loading/failure states reuse the existing shadcn components and authenticated page boundary. Cached market value, unrealized P/L, allocation and freshness are available through the separate valuation API; browser integration follows in 7E.

See [testing](testing.md) for browser and PostgreSQL verification, and [security and deployment](security-and-deployment.md) for the runtime boundary.
